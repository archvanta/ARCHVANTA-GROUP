# مدل کار و تصمیم

فاز اول از دادهٔ نمونهٔ نسخه‌دار و سوابق محلی در مرورگر استفاده می‌کند. این قرارداد برای تعیین معنای وضعیت‌هاست. شناسه‌ها و نقش‌های نمایشی در فاز سرور با شناسهٔ سازمان و هویت احرازشده تکمیل می‌شوند.

| موجودیت | داده‌های اصلی |
| --- | --- |
| `Department` | شناسه، نام، مدیر مسئول، نقش‌های تخصصی و مأموریت |
| `Task` | شناسه، دپارتمان، عنوان، مسئول اجرا، سطح ریسک، وضعیت، نسخه |
| `Approval` | شناسه، شناسه و نسخهٔ کار، زمان ارسال، خلاصه، پیشنهاد، محدودهٔ مجاز و اثر تصمیم |
| `Decision` | شناسهٔ درخواست، نسخهٔ کار، نتیجه، یادداشت و زمان ثبت. در سرور هویت تصمیم‌گیر و شناسهٔ درخواست تکرارپذیر هم ثبت می‌شوند. |

| نتیجهٔ مدیرعامل | وضعیت کار پس از ثبت | یادداشت |
| --- | --- | --- |
| `approved` | `ready` | اختیاری |
| `rejected` | `rejected` | دلیل الزامی |
| `changes_requested` | `needs_changes` | دلیل الزامی |

کار در انتظار تصمیم با وضعیت `awaiting_approval` و یک درخواست برای همان نسخه نمایش داده می‌شود. یک درخواست فقط یک نتیجه می‌گیرد. بعد از اصلاح، مدیر دپارتمان نسخهٔ جدید کار را با درخواست تازه ارسال می‌کند. درخواست قبلی و نتیجه‌اش به‌عنوان سابقه حفظ می‌شوند. رابط فاز اول، ثبت تصمیم را پیاده‌سازی می‌کند. ارسال نسخهٔ تازه، پیگیری اجرا و گردش کامل بازبینی در فاز سرور فعال می‌شوند.

## قرارداد فاز سرور

- `Task` و `Approval` به سازمان وابسته‌اند. خواندن و نوشتن باید با عضویت و نقش احرازشده کنترل شود.
- هنگام ثبت تصمیم، سرور وضعیت و نسخهٔ مورد انتظار کار، مجوز تصمیم‌گیر و محدودهٔ درخواست را بررسی می‌کند. ثبت نتیجه، تغییر وضعیت و درج رویداد حسابرسی در یک تراکنش انجام می‌شوند. قید یکتایی روی تصمیم هر درخواست و کنترل نسخه، اثر درخواست تکراری یا هم‌زمان را مهار می‌کند.
- رویداد اجرای کار از تصمیم مدیرعامل جداست و وضعیت اجرا، شواهد، خطا و زمان را ثبت می‌کند. اجراکننده از کلید تکرارپذیر برای تماس‌های بیرونی استفاده می‌کند و برای تغییر محدوده باید درخواست تازه دریافت کند.
- سوابق تولید در پایگاه داده نگهداری می‌شوند. مرورگر و دفتر سه‌بعدی فقط نمای وضعیت مجاز برای کاربر را از API دریافت می‌کنند.
